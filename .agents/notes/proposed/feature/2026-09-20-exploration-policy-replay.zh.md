# Agent Note: 面向探索策略的已记录运行回放

Status: proposed

[English](2026-09-20-exploration-policy-replay.md) | 中文

## 问题

本 harness 中的长时程工作由部署时固定的策略驱动。`packages/workflow/tool-ralph/src/index.ts` 中的 `ralph` 循环是一个部署方拥有的脚本文本，模型不得改动；可持续激活的子智能体扇出受 `packages/subagent/subagent/src/index.ts` 中的 `maxActiveSubagents`（默认 8）限制；单步工具批处理受 `packages/core/agent-loop/src/constants.ts` 中的 `maxParallelToolCalls`（默认 10）限制；轮次节奏受 `packages/goal/goal/src/index.ts` 中的 `maxGoalRounds` 与 ralph 的 `maxRounds` 约束。这些机制各自回答了探索策略要回答的三个问题：接下来继续推进哪一块工作、有多少并行运行、以及何时停止。它们都无法从 harness 已经记录的历史中改进。

这类策略的反馈既延迟又昂贵。判断一个调度决策需要观察整轮运行如何展开，因此比较两个候选策略的代价是各自一整轮 rollout。于是，本 harness 无法在不支付比较成本的前提下回答：「换一种批处理或停止规则，能否用更少的智能体调用达到相同结果？」

离线回答该问题所需的大部分素材已经存在。每次运行都是一个追加式的类型化日志（[会话事件](../../../../packages/core/session/src/types.ts)），由 [session-persistence-jsonl](../../../../packages/session/session-persistence-jsonl/README.zh.md) 持久化，其中包含每次尝试的结算（`assistant/attempt`）、轮次与步骤边界、带耗时的工具调用，以及委派血缘。缺失的是四样东西：附着在尝试上的分数、尝试之上的树、能在不执行任何东西的情况下遍历该树的评估器，以及一个让批处理与停止决策可编程（而非仅可配置）的接缝。

这里提出的机制取自 *Dream-RSI: Recursive Self-Improvement through Evolving Worlds*（arXiv:2609.14858，`zhengkid/Dream-RSI`）：一次已完成的运行本身就是它所能到达搜索空间上的回放模拟器，因此可以在零执行成本下离线评估成千上万个候选探索策略，只把胜出者重新部署。该论文的参考实现尚未发布，其 Python 策略契约（`see.policy.api`）属于另一个运行时，因此本提案在本 harness 既有的接缝上重新实现该机制，而不是引入那个运行时。

## 提案

按依赖顺序排列的四项能力。每一项都可独立使用；在任何策略可编程之前，A 与 B 就已经有用。

```
Recorded trees ──► replay evaluator ──► quality | cost | parallelism
                                            │
                    objective sweep + candidate comparison
                                            │
                     replay monotonicity over recorded history
                                            │
           live shadow rounds ──► replay fidelity vs prediction
                                            │
                                   human deployment
```

### A. 尝试树、决策轮与分数记录

一次尝试是探索策略可选择的一个工作单元：在本 harness 中，即一次子智能体运行，或长时程循环的一轮精炼。每次尝试成为一个节点，带有持久化身份、父节点、它所起始的工作区状态、其结果，以及由任务提供的分数。

节点以会话事件记录，因此它继承日志既有的保证（连续的 `seq`、单写者、崩溃修复），而不必另建一套存储。树的形状是这些事件之上的投影，风格与 `packages/session/session-projection` 中既有的投影单元一致。

策略决策是一条一等记录，而不是从节点父子关系推断出来的结果。每个决策轮记录策略观测到了什么（可选集合）、它选择了哪些节点、它请求的并行度、它是继续还是停止，以及由此产生的节点——因此「这四个尝试是同一个决策下的竞争备选」是已记录的事实，而不是重建出来的。一次尝试属于发起它的那个决策轮。基线提供方在任何策略存在之前就记录决策轮，因为固定策略同样在做这些决策。

工作区捕获是昂贵的那一部分，且当前没有持久化实现：[workspace-changes](../../../../packages/deliverables/workspace-changes/README.zh.md) 记录的是轮次粒度的 git 快照，其快照树与文件副本仅在该 Host 进程中的会话存续期间存在；而 `packages/test-support/session-snapshot/src/workspace.ts` 中的 `captureWorkspaceSnapshot` 虽完整却仅用于测试。第一版复用该测试工具集的捕获能力，并通过 `storage` 中枢存储内容寻址的产物；它不尝试增量快照。

### B. 回放评分器

`ctx.explorationReplay` 离线回答一个问题：给定一棵已记录的树与一个候选策略，该策略会揭示哪些节点、以什么批次揭示、以及它得到的已记录结果是什么？回放以确定性方式揭示已记录的子节点，而不生成新工作，因此它不进行任何模型调用，也不执行任何工具。于是评分的成本是磁盘读取，而不是智能体调用。

评分器分别报告三个组成部分，而不是给出单一数值，因为它们之间相互权衡：

```
quality      = max score over the revealed subtree
cost         = number of revealed non-root nodes (the attempts it would have paid for)
parallelism  = revealed nodes per decision round
```

除了这三个组成部分，评分器还输出计算它们所依据的轨迹，使后续更换目标函数无需重读历史：`best_score_by_round`、`best_score_by_cost`、`rounds` 与 `quality_at_budget`（在给定成本内达到的最佳分数）。组合分数 `V` 由这些产物派生，且绝不是唯一保留的东西。

组合后的回放分数沿用论文，其中 `beta1` 为工作量定价，`beta2` 奖励有效的批处理：

```
V = quality - beta1 * cost + beta2 * cost / max(1, rounds)
```

论文附录给出了等价的 Pareto 形式（`pareto_reward = pareto_auc_lambda * parallel_penalty`，其中 `parallel_penalty` 是在一次 beta 扫描上对 `effective_sequential_rounds / total_probes` 取均值）。首个实现交付加法形式，并将 `beta1`/`beta2` 保持为配置项；扫描是调用方对 `beta` 的循环，而不是新的机制。

### C. 探索策略接缝

策略是代码，不是配置：给定它已观测到的前缀，它返回下一个节点批次，并在决策轮边界处返回是否继续。遵循[能力接缝规则](../../implemented/architecture/2026-06-13-capability-seams.zh.md)，这是一个 Service Definition（`ctx.explorationPolicy`），由 harness 提供一个复现当前行为的固定提供方，因此在选定策略之前，挂载该接缝不会改变任何行为。

策略不会拿到 harness 上下文。它的契约是 `policy(observation) -> action`，其中 `PolicyObservation` 只携带决策轮序号、已观测前沿、已揭示尝试及其分数与结果、剩余预算与结构元数据，别无其它。观测被深度冻结，返回的动作在记录之前会针对前沿校验，因此隐藏节点、未揭示分数、评估器内部以及指向评分器的活引用在构造上不可达，而不是靠约定。

有两条性质是契约性的，而非建议性的。第一，**仅前缀**：策略只能读取已被揭示的节点、基线分数与结构元数据；未揭示的分数、已知最优节点 id 与绝对分数目标在构造上就不可达，因为回放只把已揭示的观测交给它。第二，**纯粹性**：策略是其观测的纯函数——不修改、不访问文件系统、不访问网络、不访问评估器、不依赖墙上时钟、不使用未播种的随机性——而评分装置会在同一观测上重跑它以检测非确定性与修改，而不是相信声明。第三，**单调选择**：已部署的策略本身在每一轮改进中都是候选，下一个被部署的策略是所有已评估修订上的 argmax，因此绝不会仅凭比其替代者更差的评分证据采纳某个修订。

策略还要规划下一次运行的形状（论文契约中的 `plan_grid`）：开设多少分支、每条精炼多深。在本 harness 中，该规划正是限定一次 rollout 宽度与深度的东西，对选择启用的运行而言，它取代了今日固定的 `maxParallelToolCalls`。除此之外它不取代任何东西：`maxGoalRounds` 仍是会话的外层轮次上限，规划中的 `rounds` 会针对它校验，超出上限的规划会响亮失败，既不绕过该上限，也不静默裁剪它——与本文件对其它部署上限给出的解决方案一致。

### D. 策略改进循环

外层循环在线运行当前策略，把完成的树追加到已记录树的历史中，然后让一个策略开发智能体重写策略代码，并对每个修订在模拟器池上做回放评分（见模拟器池一节）。该修订循环由既有部件组合而成：开发智能体是一个 `subagent` 或一段 `workflow` 脚本，候选策略在已为模型编写的插件而存在的沙箱中评估（`packages/extensions/cordis-host-runner/src/sandbox.ts` 中的 `evaluateHostCode`），重新部署使用既有的插件生命周期（`packages/boot/plugin-manager`）或一个运行时可变设置段，正如 `maxParallelToolCalls` 今日所做的那样。

哪些已记录树可以为修订评分，由保留与兼容性决定，两者都在下文「模拟器池：保留与兼容性」一节中规定。

重新部署是唯一不得在已发布 profile 中自动完成的一步：被重写的策略是模型编写的代码，因此它作为候选落地，由人工或既有审查流程批准，而不是作为自动安装的插件。

回放保真度是一个指标，而不是一个布尔值。每个线上轮次都会报告选择一致率、批量大小一致率、停止决策一致率、结果可得性、分数一致性与成本一致性，与回放所预测的内容对照；偏差超过配置容差即暂停重新部署。因此批准候选的审查者看到的是保真度报告，而不只是代码差异；偏差意味着该修订据以被选中的历史已不再描述当前部署。

## 契约性不变量

四条性质是本设计的承重主张，且每一条都由实现所暴露的内容强制，而不是仅靠审查。

1. **仅限已实现树的反事实。** 回放只在一次运行实际实现的搜索树上评估策略。它估计的是已记录节点之间不同选择顺序的价值；它不估计从未执行的枝的结果。胜出的策略只是在已记录历史之上更好，从未被证明在该运行本可到达的空间上最优。
2. **仅前缀观测。** 策略只能看到它已观测到的前沿，别的都看不到：未揭示的分数、已知最优 id、绝对目标与评估器内部在构造上不可达。
3. **策略纯粹性。** 观测进、动作出：不修改观测、不接触环境状态、不使用未播种的随机性。
4. **先回放单调，再线上验证。** 部署前 `V(P_new | H) >= V(P_current | H)`，部署后在配置容差内 `Live(P_new) ≈ Replay(P_new | H)`。选择由历史证明，部署由保真度证明，而不是由选择本身证明。

## 面向本代码库重述该机制

| Dream-RSI 术语 | 在此处的含义 |
|---|---|
| 发现树 | 一次长时程运行中被记录的尝试，以父子关系相连 |
| 可选集合 | 根节点加上每个已揭示的叶子：下一次尝试可以从哪里开始 |
| 批次 | 一个决策轮所扩展的节点，受该运行的 worker 预算约束 |
| 决策轮 | 一次策略决策：已观测前沿、选中的子集、请求的并行度，以及继续/停止的选择 |
| 在线 rollout | 真实运行：尝试真正执行，成本是智能体调用，结果具有随机性 |
| 回放 | 只遍历已记录的子节点：无模型调用、无工具执行、确定性 |
| 回放目标 | 质量减去定价后的工作量，再加上批处理奖励 |
| 策略改进 | 开发智能体重写策略代码；每个修订都通过回放评分 |
| 模拟器池 | 此前每一轮记录的、仍可回放的每一棵树，都用于为每个修订评分；产物被修剪即把该树移出池，且该排除被计数 |

## 数据模型

这里记录两种单位，而把它们分开正是对本文件此前留下的粒度问题的回答。一个节点就是一次尝试——一次子智能体运行，或长时程循环的一轮精炼——它是回放所揭示、目标函数所定价的单位。决策轮是策略行动的单位：它观测一个前沿，选择一个子集，设定并行度，并决定继续或停止。尝试是策略「选什么」，决策轮是策略「何时选」，而记录决策轮正是让选择、未选择与并行度成为事实、而不是派生行为的东西。

仍然暂时的是比此前更窄的一点：一次子智能体运行与一轮精炼是否足够可比、能够共用一个成本单位，将由阶段 1 测量；回退方案是按已记录的成本而非按数量为节点定价。

| 字段 | 来源 | 含义 |
|---|---|---|
| `nodeId` | 新事件 | 一次尝试的品牌化身份，在回放中保持稳定 |
| `parentId` | 新事件 | 本次尝试所延续的工作区对应的节点 |
| `workspaceRef` | 新事件 | 指向所捕获起始状态的内容寻址引用 |
| `outcome` | 新事件 | 终止状态，以及评估器返回的诊断文本 |
| `score` | 任务提供 | 质量信号；在任务声明之前为空 |
| `turn`、`step`、`sessionId` | 既有事件 | 把节点关联回其运行的已记录事实 |
| `rounds`、`attempts` | 派生 | 回放目标为之定价的计数，从不作为权威存储 |
| `decisionRoundId` | 新事件 | 发起本次尝试的决策轮 |
| `eligibleAtRound` | 新事件（决策轮） | 策略在选择之前观测到的前沿 |
| `selectedAtRound` | 新事件（决策轮） | 策略选中的子集；其补集即已记录的「未选择」 |
| `policyId`、`policyHash`、`policyVersion` | 新事件（决策轮） | 作出该决策的策略的不可变身份 |
| `sequenceWithinRound` | 派生 | 节点在其决策轮批次中的位置 |
| `replayable` | 树元数据 | 产物是否在保留策略下存活，以及指纹是否兼容 |

## 回放语义及其限制

- 策略只能在其历史实际到过的地方「做梦」：回放只揭示已记录的子节点，从不合成结果，因此模拟器在已实现的搜索空间上是精确的，在空间之外则是盲的（见契约性不变量 1）。已记录的结果还会随时间陈旧：一棵树可以在结构上仍然可回放，而产出其分数的模型、提示词、工具配置或环境早已改变，因此陈旧应当被视为主要失败模式，而不是边缘情况（见模拟器池一节）。
- 单调保证是回放局部的。它针对固定历史上的回放分数成立，对线上表现不作任何承诺；论文自身也警告回放上界并不是线上的停止信号。
- 确定性要求节点身份，而不是调用顺序。既有回放适配器按首次调用顺序把活跃会话绑定到已记录脚本，并已记载并发兄弟分支的绑定是非确定性的，因此允许并发分支的树必须按 `nodeId` 索引每个节点。
- 回放不会重跑循环。`llm-replay` 只替换模型流，仍会执行真实循环与真实工具；它是无密钥的测试适配器，不是模拟器，因此不被复用为评分器。

## 回放状态契约

回放从不重新执行，因此这份契约不是关于恢复状态，而是决定哪些已记录结果可以作为「今日所评估策略」的证据。只有当下列因素在已记录运行与策略将要运行的部署之间一致时，该次回放才对某个候选有效。

| 因素 | 今日的记录位置 | 回放时是否恢复 |
|---|---|---|
| 工作区内容 | 每次尝试的 `workspaceRef`（新增工作） | 是，也是唯一按尝试捕获的产物 |
| 模型、提供方、采样 | `request/header` 纪元的 `config`（`LlmCallConfig`：`model`、`provider`、`maxTokens`、`temperature`、`reasoningEffort`） | 否，仅为身份 |
| 工具集合与定义 | `request/header` 纪元的 `header.tools`、会话设置 | 否，仅为身份 |
| 提示词组成 | `system/message` 事件，加上该纪元的 `systemPromptUpdate` 标记 | 否，仅为身份 |
| 工作目录、agent 预设 | `SessionHeader.cwd`、`SessionHeader.agentPreset` | 否，仅为身份 |
| 环境与已安装包 | 未记录 | 否 |
| 随机种子与其它随机性来源 | 未记录，除非某个部件自行声明 | 否 |

因此按尝试的捕获是唯一昂贵的产物，其余一切都是可由指纹哈希的身份。不一致不会使该树作为记录失效：它使这些分数失去作为「在当前配置下运行的策略」的证据资格——这比「该树仍然可回放」是更强的主张。

## 模拟器池：保留与兼容性

循环评分所用的池是有界的，而两个保留旋钮约束的是不同的东西。树的骨架——节点身份、父子关系、结果、分数、决策轮记录——来自日志且体量很小，`workspaceRetention` 从不修剪它们；它修剪的是内容寻址的捕获产物，也就是占磁盘的那一部分，粒度到节点。产物已被修剪的树不再可回放，于是它退出模拟器池，并被计为「已排除」，而不是悄然消失；循环在它产出的每个分数旁记录池的大小与排除数量。另一个独立的改进循环旋钮 `poolDepth` 限定同时保持可回放的已完成树的数量。

每棵树还带有一个显式的 `replayable` 标记与一份兼容性指纹：模型与版本、harness 提交、策略哈希、提示词与配置哈希、工具配置哈希，以及环境指纹。池被划分为兼容树（指纹与被评分的部署一致）、陈旧树（仍可回放，但产生于不同的模型、提示词、工具配置或环境）与不兼容树（产物已被修剪，或指纹无法比较）。评分器绝不静默混合分区：它会报告每个候选是在哪个分区上评分的，且改进循环不得仅凭陈旧证据选择修订。本 harness 是开发者预览版，因此指纹频繁不同是预期之中的，分区是设计的工作组成部分，而不是预防措施。

因此池只会因显式的保留策略而缩小，绝不会作为某次运行存储设置的副作用缩小，且池的缩小在已评分的记录中可见。

| 部件 | 可复用的既有表面 | 新增工作 |
|---|---|---|
| 尝试节点 | 会话日志与持久化接缝 | 新事件类型，并入 `SessionEventMap` |
| 树投影 | `packages/session/session-projection` | 一个折叠尝试事件的投影单元 |
| 工作区捕获 | `captureWorkspaceSnapshot`、`storage` 中枢 | 持久化、内容寻址、按尝试存储 |
| 回放评分器 | `packages/core/session` 的折叠、`session-query` 的读取 | 评分器及其目标函数 |
| 策略接缝 | 能力接缝模式、`cordis.yml` 配置 | Service Definition 与一个保持行为的提供方 |
| 策略代码评估 | `evaluateHostCode` 沙箱 | 其外的评分装置 |
| 重新部署 | 插件管理器、运行时可变设置 | 选择规则与审查门禁 |

## 分数归任务所有

本 harness 完全没有评分器、评审模型、评分标准或任何质量指标；`benchmarks/` 度量的是毫秒与内存，且被明确禁止消费已记录的会话。因此本提案把分数视为任务拥有的输入，通过一个声明的评估器接缝传入，并把一切质量指标排除在 harness 核心之外。在 harness 内部发明一个替代分数会导致优化替代目标，而自我改进循环会让这种失败从暂时变为永久。

## 评分器如何聚合任务分数

以「已揭示子树中的最高分」作为 `quality` 是论文的选择，而它并不中立：最大值会奖励彩票式探索，因为一个为九十九次无用尝试付了钱、却因一个极佳节点而得到完全补偿的策略同样会胜出。对于一个尝试本身就是昂贵智能体运行的 harness 而言，这种偏置是一项决策而不是默认值，因此聚合方式是一个经过校验的评分器设置，交付四种选项：

| `qualityDefinition` | 取值 | 偏置 |
|---|---|---|
| `max` | 已揭示子树中任意位置的最佳分数 | 彩票式：一旦某个节点极佳，成本便不再重要 |
| `topKMean` | 最佳 `k` 个已揭示分数的均值 | 容忍少量胜出，而不塌缩为单点 |
| `bestAtBudget` | 在给定成本内可达的最佳分数 | 把预算显式化，而不是隐含在 `beta1` 中 |
| `areaUnderBestCurve` | 最佳分数-成本曲线下的面积 | 区分「20 次尝试达到 95」与「50 次达到 95」，而 `max` 会把两者抹平 |

`max` 仍是默认值，因为它是论文中被度量过的形式；阶段 3 决定它能否经受真实运行的检验，而上文的轨迹产物正是让这一决定无需重读历史即可做出的东西。

## 如何选择 `beta1` 与 `beta2`

目标函数取自论文，而它是唯一决定「更好」意味着什么的旋钮，因此其默认值必须给出理由，而不是一个裸数字。组合各组成部分时，质量会针对池中已记录的最佳分数做归一化，从而把 `V` 变成「相对于已知最佳结果的达成比例，减去定价后的工作量，再加上批处理奖励」；评分器仍然报告各组成部分的原始值，因此清楚自身质量尺度的任务可以直接按该尺度为 `beta1` 定价。

交付的默认值为 `beta1 = 0.01`、`beta2 = 0.005`：一百个已揭示的尝试与抵达已知最佳结果等价，而批处理最多可抵掉一半的定价工作量。一个已揭示节点的有效边际成本是 `-beta1 + beta2 / rounds`，因此在单轮策略中批处理奖励恰好抵消工作量的价格：当 `rounds = 1` 时每个节点的奖励为 `beta2`，而 `beta2 >= beta1` 会使揭示节点变得免费或有利可图，argmax 随之变成「不论质量、揭示节点最多」的策略。由于该奖励在 `rounds = 1` 时最大、其后只会被稀释，`beta2 < beta1` 正是「边际成本在任何轮次数下都保持为正」的条件，因此配置校验强制它，而不是仅以文档说明。想要不同取舍的部署应调整 `beta1`，而不是成本项的符号。

其余退化形态需要被点名，以便扫描能够识别。`beta1 = 0` 让揭示一切变得免费，argmax 于是塌缩为最大质量，且不再有任何效率主张。`beta1` 相对于已记录分数的分布过大时，最短的 rollout 会胜出；而由于已部署策略本身是候选，「什么都不改」将从此永远赢下每一轮。

两条规则让这些形态可见而非静默。扫描会报告每个 `beta` 下的 argmax，因此只在某一个 `beta` 下成立的决策会显现出来。而一棵已揭示的树为空的修订是无效的，不会被选中：单调选择比较的是已评分的修订，而什么都没有揭示的策略什么也没有评分。

## 配置表面

| 旋钮 | 归属 | 用途 |
|---|---|---|
| `beta1` | 回放评分器配置 | 回放目标中一次尝试的价格 |
| `beta2` | 回放评分器配置 | 批处理奖励的权重 |
| `maxParallelism` | 策略规划，受配置约束 | 每个决策轮的 worker 数 |
| `branchCount`、`refineCount` | 策略规划，受配置约束 | 下一次运行的宽度与深度 |
| `rounds`、`revisions` | 改进循环配置 | 外层迭代次数与每轮策略修订数 |
| `qualityDefinition` | 回放评分器配置 | 任务分数如何聚合为 `quality`（`max`、`topKMean`、`bestAtBudget`、`areaUnderBestCurve`） |
| `fidelityTolerance` | 改进循环配置 | 线上轮次与其回放预测之间允许的偏差，超过即暂停重新部署 |
| `workspaceRetention` | 存储配置 | 一次运行保留多少个节点的捕获产物；修剪只针对产物，绝不涉及树的骨架或分数 |
| `poolDepth` | 改进循环配置 | 模拟器池中同时保持可回放的已完成树数量 |

每个旋钮都是可从 `cordis.yml` 修改的、经过校验的 `Config` 字段，遵循「插件中不得有硬编码可调参数」的规则；部署上限保持固定，超出上限的规划会响亮失败，而不是被静默裁剪。

## 分期

1. **分数、树与决策轮** —— 一个长时程工作负载记录带任务提供分数的尝试节点，重启后可恢复，并同时记录基线策略所做的决策轮。本阶段同时确定唯一仍开放的定价问题（见数据模型）：报告按尝试的捕获成本与已记录树的宽度，若这些测量与尝试单位相矛盾，则改按已记录成本而非数量为节点定价。
2. **回放评分器** —— 已记录的树可离线评分；已部署策略自身的回放能复现其已记录的轨迹。
3. **离线比较（门禁）** —— 在没有策略接缝、没有重写循环的情况下，为六种必须能被区分开的策略评分：已部署的固定策略、广度优先、深度优先、随机、贪心最佳分数与成本感知。门禁的通过条件，是已部署策略的回放能逐轮复现其已记录的决策，且各替代方案的排序能被人工辩护。失败是这项努力合法的终点：项目停在一份经过度量、基于模拟的比较之上，没有可部署的收益，且阶段 4 与阶段 5 不启动。
4. **策略接缝** —— 批处理、宽度、深度与停止在一个 Service Definition 之后变为可编程。
5. **改进循环** —— 生成修订、通过回放评分，并在审查下重新部署，且每次重新部署都以线上与回放的偏差检查作为门禁。

## 曾考虑的替代方案

### 为什么不学习一个针对从未执行过的分支的模拟器？

一个针对未执行分支的学习式模型能回答更强的反事实，但那是另一个项目：它需要自己的训练信号，它引入一个其误差会被优化器利用的替代模型，而论文自身的保证是回放局部的。已记录树回放是这一主张诚实的版本；学习式模拟器必须凭它自己的证据来论证，而本文件并不主张它。

### 为什么不直接用 `llm-replay` 与快照测试装置作为模拟器？

它们把已记录的模型流回放进一个仍然执行真实工具与真实工作区的真实循环，因此并非零执行成本，也无法为会选择不同分支的策略评分；它们的脚本绑定还是按首次调用顺序，而该包已记载这在并发兄弟委派下是非确定性的。对于它们本来的用途——已发布 profile 的无密钥回归——它们依然合适，而对于反事实评分则不合适。

### 为什么不基于会话 `fork()` 血缘构建树？

`fork` 只在活跃会话的稳定边界处切分，每个边界只产生一个子会话，而会话 README 明确推迟了更深的入口树。那是用于展示与恢复的血缘模型，而不是策略可据以选择的前沿：它没有节点身份、没有按尝试的分数，也无法枚举某一决策点上的兄弟尝试。

### 为什么不通过在线运行的网格搜索来调优这些固定旋钮？

那正是本设计要避免的昂贵在线路径：每个候选都要付出一整轮 rollout，反馈只有在运行结束后才到达，而元搜索空间大到多数候选都是糟糕的。回放让这种比较不再消耗智能体调用，于是线上预算只花在胜出者身上。

### 为什么不直接采用论文的实现？

该仓库尚未发布，其策略契约是针对另一个 `see.policy.api` 运行时的 Python 实现，自带 trace pool 与网格规划器。采用它会在 harness 自身的持久化、投影、沙箱与插件生命周期之外再添一个运行时，并重复 harness 已经在做的记录工作。

### 为什么不用提示词引导取代回放来指导探索？

论文直接度量了这一点：在同等预算下，把抽象出的方向性洞见注入提示词，其表现劣于无引导的探索——因为强先验会过度约束多线程搜索。本 harness 已经承载了大量引导，因此继续加引导既是更省事的直觉，也是已被度量证明更差的做法。

### 为什么不让模型通过 agent-team 任务板来调度？

`packages/experimental/agent-team` 中由模型认领的任务是在运行时由模型选择的，不留下可评分的决策记录；回放需要批处理与停止决策是可针对同一棵树回放的代码，并且需要对同一前缀可复现。

## 验收标准

- 一次长时程运行产生一棵树，其节点携带身份、父节点、工作区引用、结果与分数，且该树在重启后可从持久化恢复，父子关系完全一致。
- `ctx.explorationReplay` 在至少两棵已记录的树上为候选策略评分，零模型调用、零工具执行、确定性：同一策略与同一批树得到相同分数，且三个组成部分分别报告。
- 回放当前已部署的策略能逐节点复现其自身已记录的轨迹，这是「已记录的树是完整的」这一自洽性检查。
- 选择规则在机制上成立：评分低于已部署策略的修订永不会被选中，且已部署策略始终在被评估的候选之中。
- 策略无法读取未揭示的分数、硬编码的胜出节点 id 或绝对分数目标；该约束由回放所暴露的内容强制，而不是仅靠审查。
- 每个新旋钮都是可从 `cordis.yml` 修改的、经过校验的 `Config` 字段；不得以 `DEFAULT_*` 常量替代可配置性。
- 被重写的策略只能经由显式审查步骤进入已发布 profile，绝不自动安装。
- 重新部署的策略，其最初的线上轮次会与该策略自身回放所预测的轨迹比较；偏差超过配置容差即标记该轮并暂停重新部署，审查者看到的是这份偏差报告，而不只是代码差异。
- 每个已记录的分数都标明它所依据的模拟器池，包括有多少棵已记录的树因不再可回放而被排除。
- 每个决策轮都记录其观测到的前沿、选中的子集、并行度、停止决策与由此产生的节点，因此同一决策下的竞争备选是已记录的事实而非推断，且已部署策略自身的决策可逐轮复现。
- 策略接收一个深度冻结的 `PolicyObservation` 并返回经过校验的动作；它无法触及隐藏节点、未揭示分数、评估器内部、环境状态或未播种的随机性来源，且在同一观测上重跑得到相同动作。
- 评分器在三个组成部分之外还报告 `best_score_by_round`、`best_score_by_cost`、`rounds` 与 `quality_at_budget`，且目标函数由这些产物派生，而不是作为唯一输出保留。
- 每棵树都带有兼容性指纹与显式的 `replayable` 标记；每个分数都标明它所依据的池分区，且不得仅凭陈旧证据选择修订。
- 线上轮次报告回放保真度——选择、批量大小、停止决策、结果可得性、分数、成本——且偏差超过配置容差即暂停重新部署。
- 文档、双语配对，以及测试策略所要求的已记录会话快照在同一变更中一并落地。

## 风险

- **目前还没有分数。** 整套机制都卡在任务拥有的质量信号上。如果项目在 harness 内部发明一个方便的替代分数，自我改进循环会去优化该替代目标并把这种失败固化下来。
- **节点粒度只在一点上仍是暂时的。** 本文件把一个节点记录为一次尝试、把一个策略决策记录为一个决策轮，因为会话粒度的节点让回放易于实现却几乎无用，而尝试粒度的节点有用却需要按尝试捕获工作区；阶段 1 仍需确定的是：一次子智能体运行与一轮精炼是否足够可比、能够共用同一个成本单位，回退方案是按已记录成本定价。
- **工作区捕获消耗磁盘。** 每次尝试一份捕获、内容寻址，是 harness 今日尚不具备的新存储增长；保留策略只修剪这些产物，树的骨架与分数在修剪后依然存在（见 D 节）。
- **已实现的树很窄。** 8 个子智能体与 10 个并行工具调用的扇出上限，限定了任何已记录的树能覆盖多少搜索空间；放宽它们会改变产品行为，且不属于本提案范围。
- **回放单调不等于线上单调。** 该保证只针对固定历史，因此被选中的修订仍可能让线上运行退步。
- **模型编写的策略代码是安全表面。** 执行与安装被重写的策略代码需要既有沙箱与一道显式审查门禁；自动安装进已发布 profile 不在范围内。
- **把回放上界误读为停止信号。** 针对已记录上界调优的策略，会在线上运行中过早停止，因为该上界并非线上最优；论文把这一点报告为线上失败模式，而非理论风险。
- **彩票式偏置。** `max` 聚合会用九十九次无用尝试去奖励一个幸运节点，这是论文的选择，却并不显然是本 harness 的选择；`qualityDefinition` 的存在正是为了让该偏置成为一项决策，而阶段 3 就是做这项决策的地方。
- **陈旧是预期中的失败模式。** 当模型、提示词、工具与环境变化时，树在结构上仍可回放，因此忽略指纹的池会让修订针对已不再描述当前部署的历史评分。
- **评估作弊是与沙箱逃逸不同的威胁。** 一个无法离开沙箱的策略仍可能操纵回放接口、请求畸形动作或利用错误处理；纯粹性与冻结的观测是覆盖这一点的契约，两者互不替代。
- **决策轮增加了记录表面。** 决策轮、前沿与策略身份是每次运行热路径上的新事件；它们必须小到不至于让记录成为运行变慢的原因，而基线提供方必须在任何策略存在之前就记录它们。

## 开放问题

- 在 ralph 式循环与子智能体扇出中，决策轮如何界定——按模型步骤、按 followup 批次，还是按显式规划？
- 由谁声明分数：任务配置、模型调用的工具，还是部署挂载的评估器插件？
- 策略应只决定跨尝试的批处理，还是也决定单步内的工具调用批处理——`executeToolCalls` 今日已经运行着一个有界池？
- 重试结算（`assistant/attempt`、`llm/retry`）会成为节点，还是仍归属于包含它们的尝试？
- 首个实现是否先放在 `packages/experimental/` 直到接缝得到验证，哪个已发布 profile 首先选择启用？
- `maxGoalRounds` 是否应作为已观测前缀的一部分暴露给策略，使规划能按剩余预算自行定尺寸？
- 一次子智能体运行与一轮精炼应按一个成本单位定价，还是按它们已记录的 token 与时间成本定价？
- 哪些指纹成分便宜到可以在每次运行时哈希，哪些属于 harness 看不到的部署配置？
- 保真度指标应属于 harness，还是属于改进循环自身的工具？
